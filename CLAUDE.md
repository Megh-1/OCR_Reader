# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Coordinate-template document extraction (IDP Phase 1): FastAPI + PostgreSQL backend, React console frontend (Vite, Tailwind v4, shadcn-style components, Fabric.js for the template canvas), Tesseract OCR. `idp-phase1-master-reference.pdf` is the spec every module was built against; its "refuse and flag rather than emit a wrong value" principle governs design choices here.

## Environment gotchas

- Tests run against a separate `idp_pipeline_test` database: the root `conftest.py` sets `DATABASE_URL` via `setdefault` **before any `app.*` import** (config reads it at import time). Never import `app` above that. The DB must exist; `tests/conftest.py` migrates it to head.
- The UI reaches the API same-origin through a proxy: `frontend/vite.config.js` in dev (target `API_TARGET`, default http://localhost:8000) and `frontend/nginx.conf` in the container. A new backend route prefix needs an entry in BOTH or the UI can't reach it. Don't let either server auto-pick a port.
- Tesseract path: `config.resolve_tesseract_cmd` tries the `TESSERACT_CMD` env var, then the default Windows install path by file check (PATH edits repeatedly failed to reach spawned processes on this machine), then `shutil.which("tesseract")` - which is how the Linux image finds it. A backslash slip in that Windows string (`\t` is a TAB) once silently broke it; `tests/test_tesseract_resolution.py` pins the exact path.
- **Docker works** (`Dockerfile`, `docker-compose.yml`, `docker-compose.fixtures.yml`, `docker/postgres-init/`). Verified with Docker Engine 29.1.3 + Compose 2.40.3 inside WSL2 Ubuntu 24.04 (Docker is not installed on the Windows side of this machine; Docker Desktop has not been tried): `docker compose up -d --build` brings up Postgres 17, Redis 7, the API, a batch worker and the console UI (`frontend/Dockerfile`: Node build, nginx serving on `FRONTEND_PORT`, default 8080, and proxying the API prefixes to `app`), all healthy, with all migrations applied in the container; `docker compose exec app python scripts/seed_templates.py` seeds a fresh database (it has no templates); a document posted to `/documents/batch` from Windows through WSL port-forwarding was processed by the real forking `Worker`, and a failed first attempt was retried after the 10 s scheduler delay against real Redis. Run from the repo root (in WSL, e.g. `cd /mnt/c/Users/Megh/Desktop/idp-pipeline`); `APP_PORT=8010` avoids clashing with a dev server on 8000:
  - `docker compose up -d --build`, then `docker compose exec app python scripts/seed_templates.py`; scale workers with `--scale worker=N` (untested beyond 1).
  - tests in a container, against the separate `idp_pipeline_test` database (a fresh volume creates it from `docker/postgres-init/`; on an existing volume run `docker compose exec postgres createdb -U idp idp_pipeline_test`): `docker compose --profile test run --rm tests`, and `docker compose -f docker-compose.yml -f docker-compose.fixtures.yml --profile test run --rm tests` to bind-mount the untracked fixtures read-only so the tests that need them run. Measured at the time of writing: 302 passed + 1 xfailed with fixtures (the same 303 tests as on Windows).
  - **Tesseract's OpenMP threads must be capped, or a Linux worker pool grinds to a halt.** Every field read is its own Tesseract process and a document runs `FIELD_OCR_WORKERS` (8) at once; by default each also starts a thread per core and they spin-wait against each other. Measured in the container (18 vCPUs): one document's OCR stage 8.7 s by default vs 1.9 s with `OMP_THREAD_LIMIT=1`; three documents at once 186-191 s EACH by default vs 4.2-4.8 s. On Windows it makes no difference (2.4 vs 2.5 s), which is why an older local measurement said OpenMP did not matter. `runtime.configure_tesseract()` now sets `OMP_THREAD_LIMIT=1` (`TESSERACT_OMP_THREAD_LIMIT`; an existing env value wins) for the API, the worker and the scripts; results are identical with and without it.
  - Batch throughput, full 22-document corpus in one `POST /documents/batch` on the containerised stack with the cap on (wall from submit to last document, so a 22-document batch includes a tail): 1 worker 10.3 docs/min, 2 workers 16.2, 3 workers 17.5, 4 workers 18.1, 6 workers 17.8. It plateaus at ~18 from 3 workers because the machine is CPU-bound (per-document time grows in step) - more workers than that buy nothing here. Before the cap: 6.4 docs/min with 1 worker. Accuracy was byte-identical in every run: 22/22 classified correctly with no hint, 584/612 fields correct (text-layer 58/58, scanned 252/261, camera 274/293), auto-approved precision 58/58, 218/218, 232/232, no wrong value auto-approved (the six accepted-wrong reads all landed in spot_check, the highest at confidence 84.9 - a 5-point margin under 0.90). Same caveats as always: one waybill, synthetic photos. Those auto counts predate the no-validator rule and the `flight_date` regex; re-run the same way after them (1 worker, 9.7 docs/min), accuracy and classification were unchanged and the split became auto / spot_check / review 38/20/0 (text-layer), 136/112/13 (scanned), 148/115/30 (camera), auto precision 100% in each.
  - The image has two targets (`runtime`, the default and last stage; `test`, which adds `tests/` and `scripts/`). `tests/fixtures/` is in `.dockerignore` and must stay out of every image. `TESSERACT_CMD` resolves to `/usr/bin/tesseract` there via `config.resolve_tesseract_cmd` (env var, then the Windows install path, then PATH).
  - **Debian's Tesseract is not bit-for-bit Windows's.** Same 5.5.0, byte-identical `eng.traineddata` (tessdata_fast), same input pixels - yet the half-resolution ID-card `id_number` reads `2024A7 PS0476G` at confidence 40 in the container and `2024A7PS0476G` at 52 on Windows, and the full-resolution read scores 90 against 89. Every accuracy figure in this repo was measured on Windows, so container numbers can differ at marginal reads; that test is a non-strict `xfail` off Windows, and `test_at_half_resolution_no_wrong_value_is_ever_accepted` holds on both (Module 7's regex rejects the space).
  - WSL2 quirks of this setup, not of the project: the WSL VM shuts down about a minute after the last `wsl.exe` session ends and takes every container with it, so keep a session open (`wsl -d Ubuntu -u root -e sleep 3600`); and `docker compose up` did not auto-pull `redis:7-alpine` / `postgres:17` here, so `docker pull` them first.
- `tests/fixtures/` is deliberately **untracked**: it holds the owner's personal ID-card photo and an air waybill PDF with real third-party contact data. Never `git add` it without explicit instruction. Tests using the card skip when it's absent.
- `git` prints "LF will be replaced by CRLF" warnings constantly; harmless (verified byte-identical for a binary PDF).
- Two path worlds on this machine: the Bash tool is Git Bash, whose `/tmp` and `/c/...` paths are invisible to `.venv\Scripts\python.exe` and to the Read tool (both want `C:\...`). Write scratch files under the session scratchpad and pass the Windows path to Python. `python3` is not on the Git Bash PATH; use the venv interpreter.
- Authoring a template without the canvas: `POST /templates` takes the same `TemplateIn` body the designer sends, and `app.utils.geometry.pixels_to_relative_bbox` converts pixel boxes (e.g. from `pytesseract.image_to_data` word positions) to the stored fractions. The designer's Upload only accepts `image/*` (a browser cannot rasterize a PDF onto the Fabric canvas); to template a PDF layout, process it once and pick it from "Document from…", which loads the server-rendered page from `GET /results/{id}/image`. A blank specimen form has no values to verify field boxes against: boxes placed from label geometry are estimates until a filled instance of the same layout is run.

## Architecture

Module-to-file map (the numbers appear in docstrings and commit messages): 1 `ingestion.py`, 2 `preprocessing.py`, 3 and 4 both `template_store.py` (3 = write/validate/persist, 4 = read queries), 5 `type_identification.py`, 6 `field_extraction.py`, 7 `validation.py`, 8 `output_compiler.py` (also owns `/results*`), 9 `review_queue.py`. `batch.py` is a queue wrapper around the same pipeline, not a numbered module.

`app/modules/pipeline.py` (`POST /documents/process`) wires the nine spec modules: ingestion → preprocessing → type identification → field extraction → validation → output compiler, with Module 9 (`review_queue.py`) catching both failure kinds (unmatched type → `new_template_needed`; each flagged field → its own `field_review`). Modules are plain functions calling each other's public functions; they do not re-implement each other.

**Two-pass preprocessing is the central design.** Module 2 runs before the document type is known, so `_process_page` preprocesses once generically to identify, then again using the confirmed template's `hints` (`page_aspect_ratio`, `ruled_form` in `schemas/template.py`). Hints default to "behave as before".

**Deskew (Module 2) has three traps, all measured.** (1) `correct_rotation` must keep the frame: it once enlarged the canvas, which pads the page and shifts every percentage-based field box - deskew then *hurt* (skew 1.5 deg: 8/29 fields uncorrected, 7/29 with the growing rotation, 25/29 with the frame kept; at 2.5 deg the growing version got the page refused). (2) Tesseract OSD reports orientation in 90-degree steps and cannot see fine skew (it said `rotate=0` for scans skewed 1.5 and 2.5 deg), so the estimator order is contour, then Hough, then OSD as a last resort - never OSD first. (3) A photo where document detection finds the page is straightened by the four-point warp and the skew estimator never runs on it. `DESKEW_MAX_ANGLE_CORRECTION` leaves a larger skew alone (probably a genuinely rotated sheet) and logs it; that value and the Hough tunables are PROVISIONAL, measured on synthetic data only. Text-native pages skip deskew entirely (`preprocess_image(deskew=False)`). `scripts/evaluate_deskew.py` reports detected vs injected angle per synthetic file.

**Page detection runs first in Module 2, then deskew, then binarization** (`detect_document_quad` -> `four_point_transform`; `DOC_DETECT_*` tunables, all provisional and synthetic-only). "No quad found" is a normal answer, not a refusal: a scan, a PDF render or a photo cropped to the page has no border, and the real ID card photo has none either, so refusing there would refuse a document that reads 2/3 correct. The refusal that matters is downstream and already exists - Module 5's anchors. Measured with a composer that puts the page on a desk (`scripts/build_synthetic_corpus.py` corners): partial frame, low-contrast desk and a dark book touching the page all give no quad; a dark mat under the page gives a *wrong* quad (the mat, 22% of the frame) that only Module 5 caught. Zero wrong values shipped in those cases, but do not treat a found quad as proof of a correct page. Known, unfixed: the outline is systematically ~4 working px (~10-16 px on a page 1700 wide) too far out, because Canny edges are dilated by a 5x5 kernel twice before the contour is taken. Insetting by that amount cuts worst-corner error from ~15 px to ~4 and raised 29-field accuracy on the 10 corpus photos from 268 to 280 of 290, but cut the lowest Module 5 anchor score per photo from a mean of 88.6 to 78.9 (`noisy_lowq` to 71 against a threshold of 70), and anchor scores are not smooth in a 1 px shift (`Not Negotiable Air Waybill` on one file scored 96, 91, 81, 64, 81 at insets 0-4 and was refused at 3). That trade is unresolved, so it was not applied - understand the anchor drop on real photos first.

**Page alignment** (`app/modules/alignment.py`, `template.landmarks`, tunables `ALIGN_*` in config, ALL PROVISIONAL). Template boxes are page fractions, which assumes the form sits at the same place on every page; it does not. Of 16 real waybills (3 printers, A4 and Letter, 8 image-only scans, 3 multi-page) ONE matched its anchors, the reference itself; the other 15 were refused because the anchor crop landed on blank paper (A4 content is ~0.91-0.94 the height of Letter's, and scans add margins). Alignment OCRs the whole page once, matches the template's `landmarks` (printed words, lower-case letters, from `scripts/build_landmarks.py`), fits a per-axis scale+shift with RANSAC (fixed seed, deterministic; data words are simply outvoted) and moves each box by that plus the median leftover of the landmarks within 0.20 of it, only when at least 3 are in range (a distance-weighted version with a minimum of 2 let one mismatched word pair decide a box and refused 4 of 10 labelled pages; the measurement is in config.py). It returns None, never a guess, below `ALIGN_MIN_LANDMARKS` (12) agreeing words, and behaviour is then exactly the pre-alignment one. Rules that must stay: (1) **the boxes that verify a page are the boxes that read it** - Module 5 uses aligned boxes whenever an alignment exists and refuses the page if they miss, even if the stored position would have passed, and `IdentificationResult.alignment` is handed to `extract_page_fields` / `extract_fields*` (re-fitted on the pass-2 page when pass 2 changed the frame, i.e. a photo warped to `page_aspect_ratio`); (2) landmarks are built only from words that recur on other documents, so the committed `scripts/landmarks/air_waybill.json` (130 words: waybill, consignee's, handling...) carries no one's details, and a test pins that; (3) the designer carries `landmarks` through load-and-save like `checks`. Cost: one full-page OCR (~1.5 s) per page, only for templates that have landmarks. Measured on the 16 files: first-page anchors passing 1 -> 12 of 16 with landmarks built from all 15 others; leave-out (build from some, test on the rest) 3 of 5 Easy and 5 of 6 Difficult first pages. **What it does NOT fix, found in the same run:** (a) a different printer's form (#4, Pioneer's own, 10 matching words) is correctly not aligned and needs its own template; (b) the SalamAir version has different column positions in part of the page (rows above the cargo table sit ~7-8% further left, the "Nature and Quantity" heading does not), so one stretch cannot fix it and its anchor 2 misses - own template; (c) pages 5-13 of the two big files are *House* Air Waybills (printed "Not Negotiable House Air Waybill"): they align but score 59-69 on the master anchor; (d) **recognised is not read**: the boxes were cut tight around the reference's own values, but a value in a table cell is right-aligned and the data row sits ~0.01 lower than a stretch predicts (cargo row at y 0.527-0.538 against a mapped box ending 0.530; "83.320" at x 0.154-0.196 against a box at 0.111-0.141), so 16-28 of 33 fields per recognised page came back flagged - not wrong-and-auto (spot-checked on four files, not labelled). Field boxes for another layout must span the whole cell, not the reference value. Anchor scoring now ignores case and line breaks (`Not negotiable` vs `Not Negotiable`), worth 59-69 -> 70+ on its own; anchors scoring 67-70 on #7, #8, #11 are an anchor-text problem (extra printed words inside the crop), not an alignment one.

**Batch processing** (`app/modules/batch.py`): `POST /documents/batch` (multipart `files`, optional `type_hint`) records each upload in `batches`/`batch_documents` (Postgres, uploads stored on the row so API and worker share only the DB), enqueues one RQ job per document on Redis and returns 202 + `batch_id` without processing; `GET /documents/batch/{id}/status` reports per-document `queued/processing/retrying/completed/failed`, `attempts`, `pages_done`, and the same body `/documents/process` returns once a document is completed. `/documents/process` is untouched (it and the worker share `pipeline.prepare_document` + `process_page`). Three things are easy to break: (1) a file that fails ingestion is `failed` on attempt 1 and NOT retried - the same bytes would fail the same way - while anything else that raises is retried (`BATCH_MAX_RETRIES`, `BATCH_RETRY_INTERVALS`); RQ runs a job's failure callback on EVERY failed attempt, so `on_failure` cannot mean "finally failed" - the job asks `get_current_job().should_retry` instead. (2) A retry resumes at the first unfinished page, saved after each page, because a finished page has already written an extraction result and review-queue entries and redoing it would duplicate them. (3) The models declare no `relationship()`, so `submit_batch` must `flush()` the batch row before adding its documents. RQ's default worker forks, which Windows cannot, so `app.worker` falls back to `SimpleWorker` there (timeouts by timer thread); retry delays need the scheduler, so it runs with `with_scheduler=True`, which takes a Lua lock - real Redis has Lua, the fakeredis stand-in needs `lupa` (`fakeredis[lua]`). Tests use in-process fakeredis + `SimpleWorker`, which does not exercise the scheduler; the delayed retry was checked once by hand across separate API, worker and stand-in processes. **Nothing has been run against a real Redis server.**

**Two renderings per page, identical dimensions** (`ProcessedImage`): `image_bytes` (binarized) is used *only* for Module 5 anchors; `field_image_bytes` (grayscale + CLAHE, optional ruled-line removal) is used for Module 6 and stored for review. Binarization is what makes header text detectable but shreds glyph strokes — never feed one rendering to both consumers.

**Templates** store bboxes as page-relative fractions and are **append-only**: `create_template_version` always INSERTs and template content is never edited or deleted. The one mutable thing is the `is_archived` lifecycle flag (`set_template_archived`); a doc_type is archived when its *latest* version is, so saving a new version un-archives it. Modules 5/6/7 must use the exact confirmed `(template_id, version)` via `get_template_version`, never "latest". `scripts/seed_templates.py` is the canonical source for `bits_goa_id_card` and `air_waybill`; re-seeding adds a version. With no `type_hint`, Module 5 scans every *unarchived* template (`list_known_doc_types`), each costing anchor OCR - the dev DB held ~170 leftover test templates from before test-DB isolation, which `scripts/prune_dev_templates.py` archives after review. A `type_hint` still resolves an archived template.

**Module 5** requires ALL anchors to pass (AND), unless the template sets `hints.min_anchors_matching` (N of M, N between 2 and the anchor count; set in the designer's Anchors tab, shown from 3 anchors up; one matching label never recognises a page); more than one matching template is `ambiguous_match`, never a pick, with two declared exceptions: one template whose anchors are a superset of the others' (`_most_specific`), and **`hints.yields_to`** (list of template ids): a template that names another stands down only when that other ALSO passed its own anchors on this page (`_after_yielding`; a hint ignores it; two that yield to each other stay ambiguous). `air_waybill` yields to `air_waybill_bkk` because its IATA-boilerplate anchors pass every Bangkok-form scan: measured on the 16 real waybills with no hint, `air_waybill_bkk`'s own "BANGKOK THAILAND" scored 59-100 on the nine Bangkok-form files and 0-37 on the Mumbai-form pages, and after the rule 9 of 9 Bangkok-form files resolve to `air_waybill_bkk` and 09/10 to `air_waybill` (before: every Bangkok scan was `ambiguous_match`). Known limit: a Bangkok-form print WITHOUT that mark (05, IndiGo) still passes only `air_waybill` and gets its boxes and profile. Anchors must be printed form labels that are identical on every document of the type, never shipment data, and must not sit close together — each crop is expanded by `ANCHOR_CROP_MARGIN_PX` (40), so adjacent anchors bleed into each other. **IATA-standard boilerplate is a bad anchor.** Two different print vendors' waybills share "Not Negotiable Air Waybill" and "Nature and Quantity of Goods (incl. Dimensions or Volume)" at nearly the same page position, so `air_waybill`'s two anchors also pass on a different vendor's blank IATA specimen (Diebold stock, 1400x1780 vs the reference's 1400x1811), which then gets the reference's field boxes laid over a different geometry: all 33 fields came back as OCR noise, correctly all `review` (batch result #81), but classified instead of refused. Anchors only prove "IATA-style waybill", never "these field boxes fit". A second waybill layout needs its own `doc_type` with anchors drawn from text the other layout lacks (the specimen prints a US export-control paragraph, "Diversion contrary to U.S. Law Prohibited", the reference does not; footers "ORIGINAL 2 (FOR CONSIGNEE)" vs "ORIGINAL 3 (FOR SHIPPER)" score only 76 against each other, so use a threshold of 0.80+ there, not 0.7). Check candidates by OCRing both renderings and grepping, not by eye. Until such a template exists, `air_waybill`'s anchors still match that specimen. **Blank anchor text is refused on save** (`TemplateAnchorIn`; `fuzz.ratio('', '')` is 100, so an empty anchor "verifies" any crop that OCRs to nothing, and the designer used to save exactly that: user-made `airwaybill_copy*` and `air_waybill_shipperName` were one empty anchor and zero fields). Reads still use plain `TemplateAnchor` so old stored templates load. **`hints.hint_only`** removes a template from the no-hint scan (it is used only as an explicit `type_hint`, which still has to pass its own anchors): required for a partial template over a layout another template covers, e.g. `air_waybill_routing` (8 fields copied from `air_waybill`), or every un-hinted upload becomes `ambiguous_match`. The designer has a checkbox for it and refuses to save without anchor text and at least one field.

**Module 6 has two paths, chosen per page by `pipeline.extract_page_fields`** (shared with the accuracy harness so they can't drift). A PDF page with a real embedded text layer (`IngestionMetadata.text_native_pages`, from `ingestion.extract_text_layers`) is read straight from its words - those whose boxes are >= `TEXT_LAYER_MIN_WORD_OVERLAP` inside the field bbox, in reading order, confidence fixed at `TEXT_LAYER_CONFIDENCE` - with no OCR and no second preprocessing pass. Two traps are handled in ingestion and must stay: invisible text (render mode 3, how OCR software makes a scan searchable) is *not* native, because it is recognition output that would be reported at full confidence; and `get_text()` coordinates are in *unrotated* page space, so they go through `page.rotation_matrix` before becoming fractions. Module 5 still OCRs anchors on the raster either way (form labels are usually vector art, not text). Everything without native text takes the OCR path below. **A text-native page of a template with a reader profile goes to the vision reader when its text-layer read is doubtful**: `extract_page_fields` reads the layer first, runs `validate_fields` on it, and if Module 7 rejects ANYTHING (a format, a check digit, a cross-field rule, a blank) calls `vlm.read_page(..., text_layer=layer)`; the page's exact words then replace the page OCR as the word reader's input (`reader.layer_tokens`, confidence 100), the render is not deskewed, and the alignment and crops still come from the raster. A reader that is unavailable leaves the page on its text-layer read (`reader: "text_layer"`, not Tesseract). Why: the boxes read the layer at fixed positions and the alignment is fitted on the printed labels, so a page whose TYPED layer sits off its cells (another print, a form fed through the printer off-centre) reads a neighbour's words and nothing in the alignment shows it. Measured on 24 hard digital pages (`scripts/build_demo_batch.py`, both forms, print misregistration and real-style formats): text layer 320 of 792 fields right with 10 wrong values at `auto` and 72 wrong spot checks; routed 738 of 792 right, none `auto`, 47 wrong spot checks and 7 in review (all 24 pages routed, ~40 s of GPU each). On the real text-native waybills: 08 and 09 (reference layout) reject 0 fields and stay on the text layer, 05 and 10 reject 16 and go to the model, 11 rejects 1 (`total_other_charges_carrier`) and goes to the model.

The OCR path: **Module 6** reads each field at several Tesseract PSMs (`PSM_CANDIDATES`, declared PSM first and wins ties), discards empty reads, keeps the most confident, and runs fields on a thread pool. A field whose `validation_regex` admits nothing but digits (`_accepts_only_digits` reads the parsed regex, so `^\d{1,4}$` qualifies and `^[\d.,]{1,10}$` does not) gets one extra read, digit-whitelisted at PSM 7 and tried last so it only wins on strictly higher confidence: Tesseract read a lone "1" as "{", the trim emptied it, and `pieces_rcp` came back blank. Never whitelist at PSM 8 or 13 - they read that "1" as "4" at confidence 68-94, a confident wrong value. A rescued read is still low confidence (20-31) and still flagged; the gain is a correct value in front of the reviewer. `ocr_responses(...)` in the tests takes a third tuple element (the regex) so mocked reads match. Edge-only trimming of rule-fragment characters is the only text repair allowed; content is never "corrected". The one exception is a selection the TEMPLATE declares (`TemplateField.from_field` / `extract_pattern` / `squash_spaces`, below): it cuts a read down or joins its whitespace and never changes a character that was read, and the derived value's confidence is that of the words it was cut from, not of the cell. Parentheses and opening quotes are trimmed by balance, not by character (`BANGALORE (BLR)` must keep its closer, `"ACME" TRADERS` its quote). Tesseract reads a cell's left border as `|`, or as an opening quote (U+201C, U+2018, straight; raw bytes are valid UTF-8, not a decoding fault) - it is easy to mistake those for replacement characters because a cp1252 console prints them as `?`. Check `ord()`, never the rendering. `Image.load()` must run before the fan-out (PIL lazy decode races otherwise).

**Field read options** (`TemplateField`, applied in `field_extraction._apply_field_options` on both Module 6 paths): `from_field` (read ANOTHER field's text once instead of this field's box; no chains), `extract_pattern` (one capture group, searched case-insensitively; the group is the value), `squash_spaces`, and `optional` (derived fields only). Built for one goods cell holding a description, an HS code and an invoice number on lines that move, and for "AS 500.00" / "176-0669 1322". Rules that must stay: the derived value's confidence is that of the WORDS it was cut from (`_confidence_of_span`; a cell averaging 85.7 had its code's digits at 30 and 25), falling back to the cell's lowest word when words and confidences do not line up; an empty selection is flagged, never accepted at the cell's confidence; a pattern must end where its value ends (`(?!\w)`), since a capture that stops at a misread character is a short, well-formed, wrong value; an `optional` blank is accepted but is NEVER auto, not even from exact PDF text, because a pattern that did not match is not proof the value is absent ("HS CODE NO. 6109..." missed a pattern once) - it enters the queue as `why: blank_optional`. The patterns live in `scripts/waybill_forms.py` with a test table (`tests/test_waybill_forms.py`).

**Module 7** flags a field if regex, checksum *or* confidence fails, collecting every reason. A field may name a `checksum` (schema `Literal`, currently only `iata_awb_mod7` on `awb_number`); it fails under its own reason `check_digit_invalid`, distinct from `format_invalid` because it catches a value that is shaped right and wrong (`176-06067726` for `176-06067736`, which a regex cannot see). An unparseable value is the regex's finding, not the check's, so pair a checksum with a regex. Mod-7 cannot catch a 0<->7 swap in the serial. Add a checksum name only for an algorithm the domain really defines, and keep the designer's load-and-save carrying it (`TemplateDesigner.jsx` rebuilds fields from its own state, so anything it does not carry is silently dropped from the new version - `checksum` and template `hints` are carried explicitly). **Approval tiers** sit on top of validation (`validation.approval_tier`, output field `approval_tier`): `review` = Module 7 rejected it, `spot_check` = accepted but under `CONFIDENCE_AUTO_APPROVE_THRESHOLD` or with no regex and no checksum, `auto` = accepted, validated (`validation.has_validator`) and at or above the threshold (a field exactly on the line is auto, like the floor). A field with no validator is never auto however confident - text-native reads included - because every wrong value Module 7 accepted on the synthetic corpus (confidence 64-87, 3-5 points under 0.90) was in such a field; the rule trusts the author, so a regex that admits anything still counts. A tier only ever adds caution: a rejected field is never promoted and a spot check does not flip `overall_status`. A reviewer resolving a flagged field clears `needs_review` but leaves `approval_tier` as the machine's own call; results stored before tiers existed read back as `None`. `pipeline.process_page` enqueues every spot_check field as its own review-queue entry (`entry_type` `spot_check`, payload `why` = `below_auto_threshold` or `no_validator`), resolved like a field_review by confirming or correcting the value; it never flips `overall_status`. The rule cost 186 correct reads their auto (text-layer auto 100% -> 66%, scanned 84% -> 52%, camera 79% -> 51%, all precision 100%); `evaluate_accuracy.py --sweep` prints what it holds back per tier. With it, auto precision is 100% at every threshold down to 0.50, so on this corpus the 0.90 guards nothing observed - it remains for shape-valid misreads in validated fields, which one waybill (29 distinct values) cannot measure, and it cannot demonstrate 99% auto precision. Enums are validated via `validation_regex` (no separate allowed-values field). Regexes must be as strict as the data: a shape-only date pattern once accepted the OCR misread `17-Oci-2006`.

**Review grouping, bulk accept and evidence** (`app/modules/review_groups.py`, `app/utils/stats.py`, `frontend/src/components/GroupedReview.jsx`; Review screen's "Grouped" view). `GET /review/groups?by=value|document[&template_id=]` gathers pending entries (same value in the same field on 2+ documents, or every pending field of one document); `POST /review/bulk` accepts spot checks in one transaction. **The server, not the UI, decides what may be bulk-accepted**: only a `spot_check` with `why` in (`below_auto_threshold`, `no_validator`), a non-empty value, still pending and not an audit sample - a `field_review` (Module 7 rejected it) and `blank_optional` are always refused, and one refusal refuses the whole request. Every bulk accept holds back a random sample (`audit_fraction`, default 10%, never under 5% and at least one when 2+) as `audit: true` spot checks that a person resolves one by one and that can never be bulk-accepted later. Resolutions carry `via` (`single` | `bulk`). `GET /review/evidence` counts ONLY `single` resolutions per (template, field): checked, changed (whitespace-normalised), and the exact one-sided Clopper-Pearson upper bound on the error rate; a bulk accept is not an independent check. At 1 error in 10,000 and 95% confidence, 29,956 clean checks are needed per field (rule of three), which the Evidence tab says plainly. **Audited auto-approval** (`app/modules/trust.py`, config `AUDITED_AUTO_APPROVAL` / `TRUST_*`): a (template, VERSION, field) whose single-checked spot checks give an upper bound at or under `TRUST_TARGET_ERROR_RATE` (1e-4 at 95% = 29,956 clean checks, so nothing is trusted on a fresh install) has its spot checks approved as `auto` with `auto_basis: trusted_field` in `pipeline.process_page` (decided before the result is stored), except a random `TRUST_AUDIT_FRACTION` (5%) enqueued as `audit: true` spot checks. Only `below_auto_threshold`/`no_validator` spot checks with a value count and qualify; a Module 7 rejection or a blank optional never does. Correcting a trusted-auto value on the Results screen writes an already-resolved spot-check row (that is the error the trust must hear about) and clears `auto_basis`. Evidence is read by one SQL aggregate, cached `TRUST_CACHE_SECONDS`. The 5% audit rate and 30 s cache are unmeasured starting figures. Design follows Learn-Then-Test / selective risk control (arXiv 2110.01052, 2608.14639): split by document, never refit the score on the calibration data, certify with an exact binomial tail.

**Review scope, group correction, accept-agreed and the clear buttons** (`app/modules/review_groups.py`, `app/modules/housekeeping.py`, `ReviewQueue.jsx`, `ConfirmDialog.jsx`). (1) **Batch scope**: `GET /review`, `/review/groups`, `/review/agreed`, `POST /review/clear` take `batch_id`; the scope is what the batch's documents stored (`batch_documents.result.pages[*].extraction_result_id`, `review_queue_id` for a refused page), via `review_queue.batch_scope`. The Review screen opens on the NEWEST upload (`#/review`), `#/review/<id>` is one upload, `#/review/all` everything; the sidebar badge stays global. (2) **`POST /review/bulk-correct`** writes one typed value to every entry of a value group (needs 2+, one field of one template version, not an audit sample), refuses a value that fails the field's `validation_regex` (`re.fullmatch`, as Module 7 does), holds a random 10% back as `audit` (now also on `FieldReviewPayload`) and resolves the rest `via: bulk`, so it is never evidence. Unlike accepting, it may take a value Module 7 rejected (`GET /review/groups?include_rejected=true`, each group says `accept_ok`). (3) **`GET /review/agreed` / `POST /review/accept-agreed`**: the server picks pending spot checks that `bulk_refusal` allows, read by the vision model (`SpotCheckPayload.reader`, recovered from the batch for older rows) at `>= VLM_GATED_CONFIDENCE`, i.e. a second reader agreed or an arithmetic fact held; then the ordinary bulk accept with its audit sample. It is a shortcut, not auto-approval: 4 of 797 such values were wrong on the 50-document batch (0.5%, 95% upper bound ~1.3%), nowhere near 1e-4, and the dialog says so. (4) **`POST /review/clear` and `POST /documents/history/clear`** need `{"confirm": true}`; resolved review entries and the results they point at are KEPT (they are the evidence `trust.py` counts), history is refused with 409 while any document is queued/processing/retrying. Tests: `tests/test_review_actions.py`.

**By-field review, strict JSON export and the honest queue size** (`FieldColumn.jsx`, `app/modules/export.py`, `FieldResult.verified_by`). (1) `GET /review/groups?by=field` lists ONE field across the upload's documents (same crop, one value per document, rejected values first); the Review screen opens on it ("By field"): fix the wrong values in place, "Accept N unchanged" (bulk accept, 10% audit hold), or "Leave blank" (`POST /review/clear` with `field_id`: deletes that field's pending entries in the batch; the values stay in the result as the machine's read and the strict export leaves them empty). (2) `FieldResult.verified_by` (`person` | `bulk`) is written when an entry is resolved (`single` -> person, `bulk` -> bulk) or a value is corrected on Results. (3) **`GET /documents/batch/{id}/export`** (Upload screen "Download JSON"): per field `{value, status, confidence}`, status `confirmed` (a person), `accepted` (bulk), `auto`, or `unverified`; strict (default) emits NULL for `unverified` with the machine's read under `suggested`, so every emitted value was either validated-and-auto or looked at by a person; `strict=false` emits everything with its status. Nothing is guessed. (4) **Queue floor measured on the 50-document hard batch**: a Tesseract second reader agrees with the model on only 55 of 624 ungated values and is right on 1 of 117 model errors, so it is NOT a gate; of ~1,518 fields ~670 stay in the queue, i.e. 20-30 items per 50 documents is not reachable at 1-in-10,000 error. What shrinks the work is grouping (By field / Same value), Accept agreed, correcting a group once, and leaving unwanted fields blank.

**Cross-field checks** (`template.checks`, `app/modules/checks.py`, run inside `validation.validate_fields`): declarative rules a person writes into the template - `product`, `sum`, `equal`, `one_of` (inline values or the built-in `iso4217` list) and `maps_to` - with optional `when` gating and a one-group regex `patterns` to compare part of a value (`EK0565/27FEB` as `EK`). No expression language, nothing evaluated as code, nothing learned. A failed check flags EVERY field it names (reason `cross_check_failed:<label>`, tier `review`) even when each passed its own checks, so it only ever ADDS caution; a check it cannot decide (an input missing, empty or unparseable, a `maps_to` key not in the table, a closed `when`) is `skipped`, not passed, because malformed inputs are the field's own format check to report. `TemplateIn` refuses a check naming a field the template lacks; old stored templates load with `checks=[]`. `air_waybill` v5 carries four (weight x rate = total only for rate class Q, since a minimum charge is not a product; flight prefix = first carrier; ISO currency; AWB prefix 176 -> EMIRATES, one pair because it is the only one we have a document for). Rules that hold on the one reference document but are not proven for the type (prepaid weight charge + agent + carrier charges = total prepaid; it ignores valuation charge and tax) were deliberately NOT added. The designer carries `checks` through load-and-save and lists them read-only; authoring is via the API/seed for now.

**The text-native path depends on the PDF producer's font metrics.** The 50%-of-word-box overlap rule reads a word's box height from the font's ascent/descent, and producers disagree: the real waybill's Verdana boxes are 9.72 pt tall at 8 pt (ascender 1.005), ReportLab's embed of the same font gave 8.0 pt (0.765). With the shorter boxes `invoice_reference` claimed the `HS CODE` line in 40 of 40 documents, and even with the right metrics a long consignee name occasionally lands in `consignee_address` (1 of 40). So a template cut from one producer's PDF is not guaranteed on another's. Center-point containment would be more robust but changes Module 6 and needs measuring first.

**Synthetic waybills** (`scripts/generate_synthetic_awb.py`): the real PDF is a full-page picture of the blank form plus a Verdana text layer, so a fake is made by redacting that text (images and line art untouched) and writing new text at the same origins, sizes and leading spaces; values that the form repeats outside any template box (AWB number top-left and bottom, the totals row, the agent's signature) are rewritten to match, so none of the source's identity survives (a test checks). Embed Verdana with PyMuPDF `insert_text`, then rewrite the font's ToUnicode CMap (`Fonts.fix_unicode`): PyMuPDF maps the hyphen glyph to U+00AD and the space glyph to U+00A0, which would fail the AWB regex, while ReportLab's embed has the wrong box height (above). A column-aligned span such as `K  Q` is split into its parts before replacing. Values come from Faker plus real IATA airline and airport codes, a mod-7 AWB number and a total that really is weight x rate. It tests different CONTENT on the same layout and font; it says nothing about another airline's form or printer.

**Template boxes derived from a PDF's text layer ignore printed labels.** Form labels are usually vector art, absent from the text layer, so a box tight to a value can overlap its label on the RASTER path even though it is perfect on the text-native path. `shipper_name` did: label ink to y=0.0509, value ink from 0.0545, box top 0.0486, so the label was OCR'd into the value. When authoring, profile the ink rows on a render (the gap was 8 px at 200 DPI) and put the edge mid-gap. The consignee box had the same problem, smaller: its top (0.1395) was 2 rows into the label's descender and the gap is 0.1400-0.1450. Moving the top to 0.1425 lifted the corpus replay from 16/19 to 19/19 (0.1410 and 0.1440 both give 18); moving the bottom edge as well dropped it to 10/19, so only the top moved (`air_waybill` v8).

**Reader engines are configuration** (`app/modules/vlm_reader/engines.py`, `openai_client.py`, `config/reader_engines.example.json`). Which model reads a page's crops is a named entry in the JSON file `READER_ENGINES_FILE`; `READER_ENGINE` (env) picks one, else the file's `default`, else its first entry. Kinds: `service` (our `/read` protocol, `scripts/gpu/serve_reader.py`) and `openai_compatible` (any server speaking `/chat/completions` with image input: vLLM, SGLang, Ollama, a hosted model; `model`, `concurrency`, `max_tokens`, `extra_body`). Tokens come from `token_env` (an env var NAME), never the file. With no file, `VLM_READER_URL`/`VLM_READER_TOKEN` make one engine `default` of kind `service`, so old deployments are unchanged. Both kinds answer `read(items, max_new) -> replies`, all-or-nothing; a registry or engine that cannot be used is `ReaderUnavailable`, so the page falls back to Tesseract exactly as before (`reader: "ocr_fallback"`), never a crash. The engine that read a page is logged (`VlmPage.engine`), not yet stored on the result. Limits to remember: the PROMPTS (`waybill.py`) are the ones the shipped adapter was trained on, so a different model may need its own wording (measure with `scripts/evaluate_reader.py` first); switching engines changes who reads, so the human-check evidence `trust.py` counts was gathered on another reader (vision-read pages never get audited auto-approval anyway); the fixed gated/ungated confidences apply to every engine, so a new engine is a spot check until measured. A whole-page parser that returns text without positions (e.g. Baidu's Unlimited-OCR, 2026, a long-document model served by vLLM/SGLang) does not fit the crop-reader interface as a page reader; as a crop reader it is zero-shot (no adapter for our forms) and is only a candidate until `evaluate_reader.py` scores it. Tests: `tests/test_reader_engines.py`.

**Engine selection** (`app/modules/engine_selection/`, rules in `docs/engine-selection.md`, OFF unless `ENGINE_SELECTOR_ENABLED=1`; migration 0007). `select_chain(template_id, probe features)` picks the chain per template: manual override (`ENGINE_CHAIN_OVERRIDES_FILE`, off by default) > measured (PROMOTED engines scored on >= `ENGINE_MIN_FIELDS` fields, not drifted, ranked by field accuracy, ties within 0.005 by speed) > cold start (configured readers by kind prior, `force_review`: `validation.demote_auto` caps the page at spot_check and `trust.py` is skipped). `text_layer` leads for pages with a text layer, `tesseract` is always last. Scorecards are stored per (template, engine, corpus) by `evaluate_reader.py --save`; `--promote` promotes a candidate only if it beats the best incumbent by 0.01 on the SAME corpus with no wrong value at auto (an incumbent without a card on that corpus blocks promotion: run it in the same command). Drift = live single-checked review entries (`payload.engine`) under the scorecard's queued accuracy by 0.05 over >= 50 checks. Two readers: disagreement always sends the field to review; agreement raises trust only once the PAIR was measured (>= 200 agreed, <= 0.5% wrong), and even then a value is only gated (89), never auto. Every chain change is logged with its numbers (`engine_chain_log`). People's one-at-a-time corrections become `labelled_examples`; `scripts/export_labelled.py --template ID --out DIR` turns them into an evaluate_reader corpus (review-size renders of QUEUED fields, so an uncertain-field score, not comparable across corpora). Not measured: handwriting share (None, no rule reads it) and language beyond the script of a text layer; probe quality thresholds are provisional. Nothing here has run against a real second model yet. Tests: `tests/test_engine_selection.py`.

Rules that must stay in the experiment: a crop that cuts a value off is answered EMPTY in training, never with the visible part; the 5 real held-out waybills (01 03 13 14 07) are contaminated, documents 04 05 15 16 are the clean never-read ones, and the labels in `data/real_awb/labels/` are unverified drafts; choose an adapter or epoch on SYNTHETIC validation only, then read real pages once. Experiment tooling in `scripts/`: `make_train_set.py` (`IDP_FORM=B|M`, `IDP_ROUND=4` the newest recipe), `make_eval_crops.py`, `score_samples.py` (synthetic) and `score_vlm.py` (real pages), `--varied` on `synth_bkk.py` / `generate_synthetic_awb.py` (real-style formats, fonts, overflowing values; formats from TRAIN labels only), `scripts/gpu/` (trainer: gradients summed by hand over `torch.distributed`, no DDP wrapper, out-of-memory samples skipped; rebuild notes in the memory file `gpu-box-constraints`; the GPU box was cleaned and its adapters are at `data/models/wb_v4_epoch3` (chosen) and `wb_v3_epoch2`). Measured round 4: synthetic validation 94.6% (previous adapter 92.9% on the same crops); real held-out 89.1% against 89.7%, i.e. no measured gain on real new pages; the old Tesseract pipeline gets 11% on the same pages.

## Tunables live in `app/config.py` — and are measured

Nearly every constant there carries a comment with the measurement behind it. Don't change one on intuition, and don't tune off a single sample; re-measure. Non-obvious ones: `FIELD_CROP_MARGIN_PX = 0` (tight PDF-derived boxes + any margin drags neighbouring labels in), `OCR_TARGET_LONG_EDGE_PX` (upscaling *hurts* OCR; never shrinks), `PDF_RENDER_DPI = 200` (72 was default and far worse; 300 also worse), `MAX_UPSCALE_FACTOR` (phone photos embed a meaningless 72 DPI tag that once triggered a decompression-bomb crash), `DOC_DETECT_MIN_BORDER_CONTRAST` (without a border gate a scan's own printed form border is "detected" as the page and the content is cropped away). It is measured as thin-band contrast (`border_contrast`): the median brightness of a narrow band just inside the candidate outline against a matching band just outside it, each set `DOC_DETECT_BAND_SKIP_PX` off the outline because the dilated-edge outline overshoots the true edge by ~4 px. It replaced a whole-inside vs whole-outside mean gap, which on a page whose printed border was the candidate measured INK DENSITY: the waybill's own border read 9-22 against a gate of 25, and a page with 3.5x its ink read 52.6 and was accepted as photographed (on a near-white desk it got a wrong quad, its own printed border). On synthetic data the new measure reads 0-3 for printed borders, 76-146 for the corpus photos and ~0 for inky pages regardless of ink, and moved no quad, Module 5 outcome or field value across the 20-file corpus plus the two real files. **The 40 is NOT validated**: it is a better design with a number chosen from one waybill's synthetic composites (picked to keep the old gate's light-desk operating point, a desk ~215 against white paper), and it needs a pass on real photographed pages before it is trusted. It cannot tell a page edge from any other real edge - a dark mat under the page reads 71 and is accepted; only Module 5's anchors refuse that quad. `tests/test_page_detection.py` runs every behaviour at a light and a dense fixture page so the ink dependence cannot return).

## Testing conventions

- Most tests mock `pytesseract`; `tests/test_risk_mitigations.py` runs **real** OCR against the reference doc's risk table. Real-OCR assertions on measured behaviour should stay real.
- To prove a path runs no OCR, patch `pytesseract.pytesseract.run_tesseract` (the subprocess every pytesseract API goes through), not just the wrappers - see the `no_tesseract` fixture in `tests/test_text_native.py`.
- Alembic's `fileConfig` defaults to `disable_existing_loggers=True`, which mutes every `app.*` logger when migrations run in-process (the test session does); `alembic/env.py` sets it False. If `caplog` sees nothing, check `logger.disabled`.
- Patching files from Python on Windows: ALWAYS pass `encoding="utf-8"` to `read_text`/`write_text`. The default is cp1252, and inserting a non-ASCII character that way put a lone 0x85 byte (a cp1252 ellipsis) into `TemplateDesigner.jsx`, which shipped as "Start a new template�". Prefer `\u2026`-style escapes in source, and scan for `UnicodeDecodeError` after a bulk edit.
- Never import `app` in an ad-hoc script *before* calling `pytest.main`: it bypasses the root `conftest.py` and the tests write into the dev database.
- `extract_field` calls `image_to_data` once per candidate PSM, so mocks must return one response per mode — use `ocr_responses(...)` from `tests/test_field_extraction.py` (derived from config) rather than hardcoding a call count.
- Tests seed templates from `scripts/seed_templates.py`, not copies, so tests can't drift from what ships.
- `scripts/evaluate_accuracy.py` must measure the real pipeline path, so it calls `pipeline.preprocess_for_template` rather than re-implementing the second pass; keep the two in sync by keeping it that way. Its ground truth for real documents lives in untracked `tests/fixtures/`.
- Extraction accuracy figures in commit messages come from a synthetic "haywire photo" harness (clean render composited on a desk background); real printed/photographed waybills are not yet measured.
